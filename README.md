# Сайт «МЁДВЕДЬ»

Исходный код новой версии сайта петербургского производителя медовухи, сидра и пуаре «МЁДВЕДЬ». Сайт знакомит с напитками, производством и компанией, содержит контакты для покупателей и оптовых клиентов.

## Что реализовано

- Главная страница с обзором продукции и компании.
- Каталог и отдельные страницы категорий: медовуха, сидр и пуаре.
- Страницы о компании, производстве и контактах.
- Страница HoReCa с ассортиментом, форматами тары, географией поставок и обращением в отдел продаж.
- Политика конфиденциальности и страница ограничения ответственности.
- Подтверждение возраста посетителя с сохранением выбора в браузере.
- Плавная прокрутка всех страниц через Lenis; анимация отключается при системной настройке «уменьшить движение».

Страницы и данные каталога находятся в репозитории. Сборка заранее создаёт HTML для каждого адреса из [структуры сайта](docs/site-structure.md), а браузер подключает интерактивность через Vue 3. Форма обратной связи обрабатывается PHP на хостинге; CMS нет.

## Локальный запуск

Используйте Node.js 24 и npm 11: версия Node указана в `.nvmrc`, требования обеих версий — в `package.json`. `.npmrc` останавливает установку в несовместимой среде. При использовании nvm установите нужный Node, затем зависимости:

```bash
nvm install
nvm use
npm ci
npm run dev:original
# либо клиентский вариант:
npm run dev:client
```

Обе команды используют один код рабочей ветки `staging`. Вариант запуска выбирается явно: `dev:original` или `dev:client`. Команда `npm run build` по умолчанию выбирает `original`; переменная `SITE_VARIANT` принимает только `original` или `client`. Для сборки доступны `npm run build:original` и `npm run build:client`. Цвет и слоган заданы в `src/data/site-variants.js`; aliases Vite подключают только выбранные компонент и данные слайдера. Настройка одинакова для готового HTML и браузера, переключателя для посетителей нет.

Если Node 24 установлен через Homebrew, выберите его для текущей сессии терминала перед командами проекта:

```bash
export PATH="$(brew --prefix node@24)/bin:$PATH"
node --version
npm --version
```

Для проверки собранной версии:

```bash
npm run build
npm test
npm run preview
```

Для локальной проверки обработчика формы нужен PHP CLI 8.4 или 8.5 с расширением `mbstring`:

```bash
php -l public/api/contact.php
npm run test:api
```

Тесты запускают временный PHP-сервер и подменяют системную отправку почты: настоящие письма не отправляются. Запускать PHP как фоновый сервис не требуется.

### Оформление Яндекс.Карты

Карта на странице контактов использует светлые и акцентные цвета темы соответствующей версии сайта и собственную метку «МЁДВЕДЬ». Для её подключения создайте `.env.local` по примеру `.env.example` и заполните `VITE_YANDEX_MAPS_API_KEY` ключом JavaScript API Яндекс.Карт v3. После изменения переменной перезапустите сервер разработки или пересоберите сайт. Без ключа и при ошибке инициализации показывается обычная встроенная карта.

Ключ используется в браузере и попадает в сборку. В кабинете Яндекса ограничьте его разрешёнными доменами, включая адрес локального просмотра. При сборке в CI передавайте эту переменную в окружение шага сборки: локальный `.env.local` не переносится в GitHub Actions. Настройку ключа и условия использования см. в [документации Яндекса](https://yandex.ru/maps-api/docs/js-api/quickstart.html).

## Автоматические проверки

```bash
npm run lint
npm run audit
npm run test:deploy
npx playwright install chromium
npm run build
npm test
npm run test:browser
```

ESLint проверяет Vue, JavaScript и служебные скрипты. Неиспользуемые переменные пока дают предупреждение; ошибки останавливают CI. Аудит зависимостей останавливает CI при известных уязвимостях уровня high или critical, включая инструменты сборки; исправления зависимостей применяются отдельно после проверки совместимости. Тестам публикации нужны локальные rsync и POSIX shell.

Playwright проверяет Chromium с настольным и мобильным размером экрана: прямые адреса, ошибки JavaScript и гидратации, подтверждение возраста, меню, слайдер, выбор объёма и сценарии формы. HTTP-ответы формы подменены, реальные письма не отправляются. Скриншоты, видео и трассировка отключены. Браузерные тесты используют готовый `dist/`; при нестандартной сборке передавайте то же значение `SITE_BASE`. Например: `SITE_BASE=/ npm run build`, затем `SITE_BASE=/ npm run test:browser`.

Workflow `checks.yml` проверяет pull request в `main` и `testing`. Workflow публикации вызывает те же проверки при push в эти ветки, независимо от `TIMEWEB_ENABLED`. Для обоих вариантов проверяются production в корне и подкаталоге, staging в корне, а PHP API — на PHP 8.4 и 8.5. Локальная версия PHP может отличаться от матрицы CI; тесты не подтверждают доставку писем и права на реальном хостинге.

Повторная успешная отправка ограничена интервалом 10 секунд в рамках одной PHP-сессии. Ограничение зависит от cookies: новый браузер или сброс cookies начинает отдельную сессию. Используется стандартное хранилище сессий PHP; отдельный файл лимита рядом с `public_html` не нужен. Ошибки идут в журнал PHP и не попадают в JSON-ответ. Таймаут браузера — 15 секунд, он не отменяет уже начавшуюся серверную отправку.

Готовые файлы появляются в `dist/`. Карты исходников (`sourcemaps`) в сборку и публикацию не включаются; локальный режим разработки сохраняет обычную отладку Vite. По умолчанию сборка использует базовый путь `/freelancet-medved/`; для размещения в корне домена задайте `SITE_BASE=/ npm run build`. На хостинге должны работать PHP и правила Apache из `public/.htaccess`.

Все изменения делайте в рабочей ветке `staging`: общее — в общих компонентах, отличия — в настройках варианта или его слайдере. Перед передачей проверяйте оба варианта. Обычный push в `staging` не запускает проверки или публикацию. Готовую пачку переносите через pull request `staging → testing`: после проверок и слияния обновляется `https://test.medved.beer/` и запускается Lighthouse. Затем pull request `testing → main` публикует основной сайт. Оба домена Timeweb всегда получают `client`; `scripts/deploy-timeweb.mjs` отклоняет оригинальную сборку, отсутствие маркера `site-variant.json` и неподходящий базовый путь до подключения к серверу. Открытый pull request в `testing` или `main` запускает проверки при новых коммитах в его исходной ветке. Старые `develope/client` и ветка `slider-3d` остаются историческими снимками, работа над вариантами ведётся в `staging`. Подробнее — в [инструкции по публикации](docs/deployment.md).

При сборке PNG и JPEG, импортируемые из `src/assets/`, преобразуются в WebP, если результат меньше исходного файла. Для текстур этикеток импорт с `?url&lossless` включает WebP без потерь и изменения разрешения, в том числе для файлов из `materials/`. Импорт GLB с `?url&optimize` сжимает встроенные PNG-текстуры в WebP без потерь через `EXT_texture_webp`, сохраняя геометрию и материалы. Исходные файлы не меняются; SVG и файлы из `public/` не обрабатываются.

### Lighthouse на опубликованном сайте

После успешной публикации отдельный аудит проверяет соответствующий сайт: из `main` — `https://medved.beer/`, из `testing` — `https://test.medved.beer/`. В GitHub Actions выполняются три последовательных замера мобильного профиля и три настольного. Он не является условием публикации и не вводит пороги баллов. Сбой самого аудита виден как ошибка отдельной проверки; уже выполненная публикация не отменяется.

Для повторного замера без нового коммита откройте **Actions → Lighthouse site audit → Run workflow**, выберите ветку и окружение `production` или `staging`. Сводка содержит медианы трёх замеров и диапазон баллов скорости; HTML и JSON каждого запуска доступны в артефакте `lighthouse-production-…` в течение 14 дней. Проверяется главная страница с заранее подтверждённым возрастом, включённой Метрикой и холодным кешем; расширения браузера не установлены. Мобильный профиль — эмуляция Lighthouse, не физический телефон. Слайдер использует статичные прозрачные слои; WebGL на опубликованном сайте не запускается.

Lighthouse 13.4.1 устанавливается только во временный каталог машины GitHub; в зависимости сайта и его сборку не добавляется. Chrome предоставляется средой GitHub, его версия записывается в отчёты. Нагрузка машины, сеть и внешние сервисы могут менять результаты; сравнивайте несколько замеров одного профиля. Локальный запуск Lighthouse для этого процесса не требуется.


## Яндекс Метрика

Счётчик `113558843` подключается при production-сборке: скрипт находится в `<head>`, резервный пиксель для браузеров без JavaScript — в `<body>`. Код и цели собраны в `src/utils/metrika.js`. Сохранены настройки предоставленного кода: Вебвизор, карта кликов, учёт внешних ссылок, точный показатель отказов и контейнер электронной коммерции `dataLayer`. События покупок сайт не отправляет.

В режиме разработки и при `SITE_ENV=staging` код счётчика не вставляется. При локальном просмотре production-сборки JavaScript дополнительно проверяет домен: загрузка Метрики разрешена только на `medved.beer`. В кабинете оставьте фильтр «Принимать данные только с указанных адресов» для `medved.beer`, без включения поддоменов. При просмотре production-копии без JavaScript резервный пиксель всё равно делает запрос; фильтр адресов нужен, чтобы такие посещения не попадали в отчёты.

В настройках счётчика создайте четыре цели типа «Целевое событие» (JavaScript-событие) с точными идентификаторами:

| Идентификатор | Когда отправляется |
| --- | --- |
| `contact_phone_click` | Клик по ссылке телефона |
| `contact_email_click` | Клик по ссылке электронной почты |
| `contact_form_success` | Сервер подтвердил успешную отправку формы |
| `contact_form_error` | Ошибка сервера, запроса, разбора ответа или тайм-аут формы |

У ошибки передаётся только техническая причина `reason`: `server`, `request` или `timeout`. Тайм-аут означает отсутствие подтверждения в браузере, а не доказанный отказ доставки. Ошибки заполнения полей и отмена запроса при уходе со страницы не считаются технической ошибкой отправки. Имя, телефон, почта и сообщение из формы в параметры целей не передаются. Отсутствие или сбой Метрики не блокируют форму и ссылки. Эти цели дополняют статистику посещений; настройку и получение данных в настоящем кабинете нужно проверить после публикации.

Браузерные тесты целей используют подмену `ym` и блокируют запросы к Метрике. В рабочий счётчик тестовые события не поступают.

## Структура репозитория

- `src/pages/` — страницы и их собственные компоненты, сгруппированные по разделам сайта.
- `src/components/` — общие элементы интерфейса; `product-scene/` содержит служебную сцену лабы и экспорта.
- `src/three/product/` — загрузка моделей, материалы, этикетки, освещение и общий координатор 3D-сцены.
- `src/three/glass-lab/` — экспериментальная оптика стакана; используется лабой и служебным экспортом статичных рендеров.
- `src/data/` — каталог, маршруты, навигация, партнёры и тексты юридических страниц.
- `src/assets/` — изображения, логотипы и шрифты.
- `src/styles/` — общие стили.
- `scripts/` — генерация страниц и проверки; `scripts/vite/` — обработка изображений при сборке.
- `tests/browser/` — браузерные сценарии и безопасные подмены API.
- `docs/` — материалы о структуре, дизайне и плане работ.

Сайт собирается с помощью Vite, а стили используют Tailwind CSS. Настройки базового пути и подключение плагинов находятся в `vite.config.js`.

В обеих версиях сайта используется общий слайдер со статичными фотографиями бокалов. Three.js, 3D-модели и мастерские не подключаются к страницам опубликованного сайта. Мастерская `materials/models/product-render-lab.html` использует общий `src/three/product/product-renderer.js` и два независимых назначения: `slider` — отдельные объекты с фронтальным светом, `slider-combined` — цельная композиция с прежним светом и расстановкой. Назначение рендера не зависит от варианта сайта. Экспорт и ограничения замены изображений описаны в [мастерской рендеров](docs/render-workshop.md). Эксперимент Cycles сохранён в `materials/experiments/cycles/`. `materials/models/brand-logo-lab.html` — отдельная лаба логотипов с экспортом PNG и GLB.
