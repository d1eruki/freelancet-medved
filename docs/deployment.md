# Публикация на Timeweb

Публикацию выполняет `.github/workflows/deploy-timeweb.yml` при push в `main`, `testing` или ручном запуске workflow для одной из этих веток. Сначала вызывается общий `.github/workflows/checks.yml`: линтер, аудит зависимостей, тесты публикации, HTML и браузерные сценарии для production в корне и подкаталоге и staging в корне, а также PHP API на PHP 8.4 и 8.5. Оба варианта (`original`, `client`) проходят HTML и браузерные проверки. Только после успешных проверок создаётся сборка `SITE_VARIANT=client` нужного окружения для корня домена, затем `scripts/deploy-timeweb.mjs` загружает `dist/` через SSH и rsync.

Общие проверки также запускаются на pull request в `main` и `testing`, не используют SSH-секреты и работают при `TIMEWEB_ENABLED=false` или отсутствующей переменной. Ошибка любой проверки блокирует job публикации. Запрет слияния при неуспешных проверках настраивается отдельно в правилах защиты веток GitHub; наличие workflow само по себе не запрещает слияние. Node.js берётся из `.nvmrc`, npm должен соответствовать требованиям `package.json`.

- `main` публикуется на `https://medved.beer/` в `TIMEWEB_PATH`.
- `testing` публикуется на `https://test.medved.beer/` в `TIMEWEB_TEST_PATH` со значением `SITE_ENV=staging`.
- Ручной запуск из любой другой ветки не публикует сайт. Одновременные публикации одной ветки выполняются последовательно; ветки используют разные группы очереди.

После загрузки `testing` workflow дополнительно проверяет публичные HTTP-ответы: главную, контакты, доступность клиентских скриптов, заголовок запрета индексации, перенаправления внутри тестового домена и ответ PHP API на GET. Эта проверка не отправляет письма. При её ошибке workflow завершится неуспешно, но уже загруженные тестовые файлы останутся на сервере для диагностики. Тестовая сборка явно задаёт `DirectoryIndex index.html`, чтобы первоначальная заглушка Timeweb `index.htm` не имела приоритет; сама заглушка не удаляется.

## Настройка GitHub Actions

- Переменные: `TIMEWEB_ENABLED=true`, `TIMEWEB_HOST`, `TIMEWEB_USER`, `TIMEWEB_PATH`, `TIMEWEB_TEST_PATH`.
- `TIMEWEB_PATH` и `TIMEWEB_TEST_PATH` — абсолютные пути к разным каталогам сайтов, заканчивающиеся на `/public_html`, без `..`, пробелов и симлинков в пути. Тестовый каталог не должен находиться внутри публичного каталога основного сайта, и наоборот. Проверка путей выполняется до сборки и подключения по SSH.
- Для текущего аккаунта основной путь — `/home/c/cl273611/public_html`, тестовый — `/home/c/cl273611/MEDVED_TEST/public_html`. Регистр букв в `MEDVED_TEST` существенен. Каталоги должны быть заранее созданы и привязаны к соответствующим доменам в Timeweb.
- Секреты: `TIMEWEB_SSH_KEY` и `TIMEWEB_KNOWN_HOSTS`. Проверка ключа SSH-сервера обязательна.
- У пользователя SSH должны быть права записи в `public_html` и его родительский каталог. На сервере нужны POSIX shell, rsync, `mktemp` и стандартные файловые команды; Node.js на сервере не нужен.

## Проверка изменений перед основной публикацией

1. Все изменения делайте в `staging`, где находится общий код и оба варианта сайта. Запускайте `npm run dev:original` или `npm run dev:client`; общую правку достаточно внести один раз. Для публикации создайте pull request `staging → testing`. Обычные push в `staging` не запускают проверки и выкладку. Проверки запускаются для pull request и повторно после слияния в `testing`, затем публикуется клиентский тестовый сайт и выполняется Lighthouse. Новые коммиты исходной ветки открытого pull request в `testing` или `main` снова запускают проверки.
2. Проверяйте прямые адреса, перенаправления и формы. API-тесты в workflow проверяют обработчик локально; они не доказывают доставку писем и совместимость с ограничениями PHP на Timeweb. Тестовый сайт использует собственную копию обработчика; сейчас он отправляет настоящие письма на `info@medved.beer`, поэтому явно помечайте тестовые обращения.
3. После успешной проверки создайте pull request из `testing` в `main`. Слияние запускает публикацию основной версии. Для переноса всей серии изменений сохраняйте историю ветки через обычное merge-слияние.
4. После основной публикации подтвердите работу формы и получение письма. При регрессии отмените конкретный проблемный коммит в `main` и опубликуйте отмену; не переписывайте историю общей ветки. Перенесите отмену также в `testing` и рабочую `staging`.

Обновлённые workflow должны попасть в `testing` и `main` обычными pull request из `staging`. До переноса каждая ветка выполняет сохранённую в ней версию workflow. `develope/client` сохраняется как исторический снимок, дальнейшие правки версий делаются в единой `staging`. Само переименование ветки не публикует незакоммиченные изменения. Переменные, секреты GitHub и настройки Timeweb менять не требуется; при необходимости защита `testing` и `main` настраивается отдельно.

Вариант сайта (`SITE_VARIANT=original|client`) и окружение (`SITE_ENV=production|staging`) независимы. Оба домена Timeweb собираются командой `npm run build:client` с `SITE_BASE=/`. Сборка создаёт `dist/site-variant.json` с вариантом, окружением и базовым путём; `scripts/deploy-timeweb.mjs` до SSH/rsync требует клиентский маркер, корневой путь и совпадающий атрибут HTML. Оригинальную сборку этот скрипт не публикует, включая ручной запуск.

Тестовая сборка направляет серверные перенаправления на HTTPS-поддомен `test` основного домена из реестра маршрутов. Явная схема HTTPS исключает редирект на HTTP при обработке запроса Apache за прокси Timeweb. Канонические метаданные и sitemap продолжают ссылаться на основной домен из общего реестра маршрутов. Все тестовые HTML до выполнения JavaScript содержат `noindex, nofollow`; Apache дополнительно отправляет `X-Robots-Tag: noindex, nofollow`, действующий независимо от клиентского обновления метаданных. Для этого нужен модуль Apache `mod_headers`. `robots.txt` разрешает чтение страниц для обработки запрета индексации, но не содержит ссылку на sitemap. Это не ограничение доступа: тестовый сайт остаётся публичным.

Основная сборка по умолчанию использует `SITE_ENV=production`; запрет индексации тестового окружения в неё не попадает. Формы и PHP-настройки тестового сайта следует проверять с той же версией PHP и изоляцией, что и на основном. Форма ограничивает повторные успешные отправки интервалом 10 секунд в рамках PHP-сессии. Для неё используется стандартное хранилище сессий PHP; отдельный файл лимита рядом с `public_html` и специальная проверка прав на его создание не требуются.

## Очистка устаревших файлов

1. Скрипт читает список предыдущей публикации из `.medved-deploy-manifest.json` рядом с `public_html`, вне публичного каталога сайта.
2. Проверяет список, пути и наличие готовой сборки. Симлинки в путях загружаемых и удаляемых файлов запрещены.
3. Загружает новую сборку через `rsync --delay-updates`, без `--delete`.
4. Только после успешной загрузки удаляет файлы, которые были в предыдущем списке, но отсутствуют в новой сборке.
5. Атомарно заменяет список на актуальный. Пустые каталоги остаются; каталоги рекурсивно не удаляются.

При первой публикации списка ещё нет: скрипт загружает сайт и создаёт список, ничего не удаляя. Накопленные до внедрения механизма файлы нужно отдельно сверить с сервером и согласовать их очистку. После первой публикации устаревающие файлы из списка удаляются автоматически.

Файлы вне списка сохраняются, например серверные настройки, вручную добавленные документы или файлы подтверждения домена. Если вручную изменить файл, уже принадлежащий сборке, workflow может перезаписать его, а при исчезновении из сборки — удалить. Изменения таких файлов следует вносить в репозиторий.

При ошибке загрузки очистка не запускается. При повреждённом списке публикация останавливается; отсутствие списка считается первым запуском. При ошибке очистки или сохранения списка прежний список остаётся для повторного запуска. Частично загруженные новые файлы при неудачной публикации могут остаться вне списка и потребовать отдельной сверки; публикация целиком не является атомарной.

## Локальная проверка

```bash
npm run test:deploy
```

Проверка обеих сборок выполняется последовательно:

```bash
SITE_BASE=/ SITE_ENV=production npm run build:client
SITE_ENV=production SITE_VARIANT=client npm test
SITE_BASE=/ SITE_ENV=staging npm run build:client
SITE_ENV=staging SITE_VARIANT=client npm test
```

Для оригинала используйте те же команды с `build:original` и `SITE_VARIANT=original`; базовый путь подкаталога также проверяется в CI. Браузерные тесты читают выбранный вариант из готового `dist/site-variant.json`.

Тесты используют временные каталоги, реальный локальный rsync и shell; подключение к серверу и секреты не нужны. Они проверяют первую и повторную публикации, сохранение серверных файлов, ошибки загрузки и очистки, повреждённый список, небезопасные пути и симлинки.
